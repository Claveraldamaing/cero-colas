A partir del documento «Resumen de Reunión Técnica - Proyecto "Cero Colas"», se presenta un análisis estructurado de los acuerdos, cambios estratégicos e impacto operativo para el proyecto:   1. Cambio Estratégico y Paradigma de IntegraciónDesacoplamiento de la base hospitalaria: La decisión técnica central es que Cero Colas no replicará la lógica interna de Pacamuro ni accederá directamente a su base de datos SQL Server.   Consumo mediante APIs: El hospital expondrá endpoints específicos para la consulta y registro de transacciones, delegando en su propio backend la lógica de negocio y generación de citas.   Rol de la base de datos local: La base de datos de Cero Colas no desaparece, pero se reduce a gestionar autenticación, usuarios, perfil local, trazabilidad, registro de solicitantes y soporte al código QR.   2. Definición del Stack Tecnológico e InfraestructuraFrontend: Desarrollado en React.   Backend: Implementado en Python con el framework FastAPI.   Motor de Base de Datos: PostgreSQL, elegido como alternativa de código abierto y sin restricciones de licenciamiento.   Despliegue y Servidor: Contenedores Docker sobre el servidor Linux del hospital, aprovechando que la infraestructura ya soporta Docker y proxy reverso.   Canal Asistido: Chatbot integrado directamente en la interfaz web. Se descarta la operadora de llamadas telefónicas por costos variables, así como ejecutar modelos LLM locales para evitar la saturación de memoria del servidor hospitalario.   3. Redefinición del Alcance Funcional (V1)Población objetivo: Enfocado exclusivamente en pacientes de consulta externa, posponiendo hospitalización para fases posteriores.   Simplificación de roles: Se restringe principalmente a los roles Paciente (registro, consulta y gestión de citas) y Administrador (supervisión y auditoría). Los roles de Médico y Admisión quedan fuera de la primera versión.   Distinción Paciente vs. Solicitante: El sistema debe registrar si la reserva la realiza un tercero (p. ej., un familiar), manteniendo la trazabilidad correspondiente.   Validación física por QR: Confirmado para que seguridad verifique el ingreso en puertas y el personal técnico agilice el llamado en consultorios externos.   4. Reglas de Negocio Clave en el Flujo de CitasIdentificación: Validación inicial por DNI mediante endpoint de Pacamuro para verificar existencia y recuperar antecedentes.   Aseguramiento y Referencias: Validación obligatoria de vigencia y especialidad de la referencia para pacientes con SIS antes de permitir la selección de cupo.   Interconsultas: Se reconoce que una cita puede originarse de una derivación interna; para la V1 bastará identificar la procedencia y especialidad destino, quedando pendiente que el hospital confirme la lógica detallada.   5. Impacto en el Modelo de Datos y RediseñoEl modelo de base de datos previamente diseñado debe ser depurado para no duplicar datos maestros ni agendas:   Persistencia local en Cero Colas: Usuarios, roles, datos de autenticación, solicitante/familiar, tokens QR, registros de auditoría/trazabilidad y notificaciones.   Delegado a Pacamuro (vía APIs): Historias clínicas, estado de aseguramiento/SIS, catálogo de especialidades, maestros de médicos, programación de cupos, disponibilidad y registro formal de la cita.   6. Cuellos de Botella y Próximos Pasos CríticosDependencia técnica: El avance del desarrollo, la arquitectura definitiva y la depuración final de la base de datos están pausados a la espera de la documentación oficial de los endpoints por parte del equipo del hospital (parámetros de entrada, estructuras JSON de respuesta, contratos de DNI y reserva).   Acciones inmediatas del equipo:Simplificar el diagrama de base de datos retirando tablas transaccionales que gestionará Pacamuro.   Ajustar la distribución de tareas y módulos entre los cuatro practicantes.   Validar con el hospital los endpoints de referencias e interconsultas en cuanto sean entregados.
